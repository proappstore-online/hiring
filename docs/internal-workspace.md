# Internal recruiter workspace

The first staff workflow is available to authenticated PAS users at `https://hiring.proappstore.online/`. Sign in with a supported PAS provider. Google is optional; GitHub remains available. A new user can create a private organization, brand and draft requisition. The creator receives the brand owner grant. Owners can add a colleague as a recruiter using that colleague's exact PAS user ID, displayed in the workspace after sign-in. Google and GitHub identities have distinct IDs and are not merged by email.

Staff can create a LinkedIn-sourced candidate/application with name, optional profile URL and email/phone, source detail, recruitment basis reference, contact context, requisition and assignee. Every application starts at `submitted`. Staff can change stage or reassign to another brand member with a reason and optimistic version check. Both changes have append-only history and audit records. Staff can add private notes and save communication drafts addressed to the candidate's recorded email. The outbox has only `draft` status and there is no send action, dispatcher, scheduled task, MAIL connection or public intake route. Drafts never contact candidates.

Migration `0003_internal_workspace` adds organization, brand, membership, draft requisition, candidate, application, stage event, note, draft outbox and audit tables. Registered PAS actions use `:__user_id` and membership checks in every read/write statement. Mutations use atomic batches; application creation writes the candidate, application, initial stage event and audit record together. Stage change requires the current stage and version. Audit rows contain actor, action, scope and operation ID, without candidate text. Lists are bounded to 100 rows. Client-supplied IDs and unique constraints make retries nonduplicating; the UI treats a zero-change result as a conflict or access failure. Tests exercise signed-in access, cross-user denial, assignment checks, stale stage changes, notes and draft isolation.

Migration `0006_optional_linkedin_profile` adds the nullable canonical `linkedin_profile_url`. The original `linkedin_url` column in applied migration 0003 is `NOT NULL` and cannot be altered under PAS additive migration rules. New records without a profile URL put `NULL` in the canonical column and an empty compatibility value in the legacy column; `list_applications` returns `NULL`. Existing URLs remain readable through the legacy column. Source detail and contact context remain required even without a URL.

Migration `0004_assignment_history` adds versioned reassignment history. Reassignment checks the target's exact PAS membership in the same organization and brand. Stage changes reject an operation ID already used by either stage history or audit, so an ID collision cannot suppress its audit record. Assignment changes share the application version with stage changes, so a stale form cannot silently overwrite either change. Application creation re-checks requisition, source, basis and contact context even when it reuses an existing candidate ID, and writes its creation audit only with this operation's initial stage event, so a replayed application ID is not audited twice. Workspace, brand, requisition and granted-member values must be non-blank after trimming. Migration `0005_operation_provenance` adds a nullable `operation_id` to notes, drafts and requisitions. Their audit rows are written only when the record was created by the same operation, so a replayed note, draft or requisition ID with a new operation ID writes no second audit row.

## Operator steps

1. Confirm main deploy applied migrations `0003_internal_workspace` through `0010_secure_multibrand_administration`, registered the actions, and uploaded the frontend. A failed migration or action registration stops the deploy.
2. Sign in at `https://hiring.proappstore.online/` with GitHub or configured Google, then create the internal workspace. Use a real organization and brand name. The initial requisition remains draft and is for internal sourcing only.
3. Have each recruiter sign in once and send the owner their displayed PAS staff ID. The owner grants that exact ID under **Workspace setup**. Do not grant access based on a matching email address.
4. Before entering live candidate data, confirm the organization's lawful basis, privacy notice, retention/deletion process, and authority to contact that candidate. The UI records basis and contact context, but policy approval is an operator responsibility.

Current limits: grant revocation, candidate editing/deletion/rights requests, attachments, public application intake and communication sending require later issues. Draft requisitions cannot be published through this workflow. The public intake gate remains closed.


## Multiple brands and administration integrity (issue #2)

The organization creator can use **Workspace setup → Add brand to this organization** to create another brand and its first draft requisition. The server derives this authority from `hiring_organizations.created_by`, never a client claim or ownership of another brand. `create_workspace` accepts an existing organization ID only for its creator; the supplied organization name does not rename it. Each new brand receives a separate owner membership. Recruiters receive access only to the exact brand granted by its owner; membership in one brand gives no access to sibling brands, including their audit records. The workspace selector lists only granted brands.

Migration `0010_secure_multibrand_administration` adds nullable brand operation provenance and database triggers rejecting audit UPDATE and DELETE statements. Existing records and migrations are preserved. Workspace setup checks identifier collisions before creating any records, and configuration audits require this operation's brand and owner membership. Member grants bind their audit marker to the exact member and scope. Every mutation rejects an already audited operation ID before writing and emits its final audit marker only after a write in the same batch. Stage and assignment history also require the preceding write to succeed. Retries and rejected administration calls leave records unchanged.

The regression suite configures sibling brands through registered actions, verifies all scoped reads and major mutations against other-brand staff and outsiders, tests mixed record IDs even for an owner of both brands, and checks relational constraints, audit attribution, replay/collisions, and populated migration upgrades. Authorization remains based on the owner/recruiter memberships; the broader `hiring_grants` schema is reserved for later scoped-role workflows. SQL reads do not produce denial/read audit events, and database triggers do not protect against an operator who can remove triggers.

Owners can publish job snapshots using passkey verification and close publications with version checks. Browse jobs and independent candidate accounts at `/?view=jobs`. Existing internal sourcing is unchanged. Assigned staff can inspect attachment metadata; reviewer file downloads remain unavailable pending trusted scanning and scoped serving. Intake stays closed.
