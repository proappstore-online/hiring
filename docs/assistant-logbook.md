# Assistant logbook in Hiring

Use the existing `log_external_action` tool with `kind: "journal"` for a manual, forward-looking entry. This records a claim about work; it does not perform the work or automatically observe MCP calls. Existing email, LinkedIn, and Discord kinds continue to record actual external actions in `external_actions`.

For a journal entry, supply `organization_id`, `brand_id`, `performed_by` (the claimed performer), `performed_at` (when the event occurred), `notes` (a meaningful short account), `operation_id` (a stable unique ID), and `params_json` as a JSON object. Its required `entry_type` is one of `action`, `observation`, `decision`, `message`, `outcome`, `uncertainty`, `pending`, or `correction`. Optional fields are `outcome`, `uncertainty`, `next_step`, `receipt_ref`, `approval_ref`, and `correction_of`. A `pending` entry needs `next_step`; a `correction` needs the original journal operation ID in `correction_of`. Link a candidate with `target_candidate_id`, an application with `application_id`, or an organization with `target_org_id`. Application and candidate links must agree and be in the authorized brand.

The app stores manual entries in the existing append-only `mcp_audit_log` with `tool_name: "manual_journal"`. The row's `timestamp` is server recording time; `input_json.occurred_at` is the supplied occurrence time. `input_json.recorder_user_id` comes from the authenticated user, distinct from `input_json.claimed_performer`. The timeline labels the source `journal` and exposes both times. Older rows without those fields remain unknown rather than being assigned inferred provenance.

Use a stable `operation_id` on retry. An exact retry makes no second row; changed content under that ID is refused. Confirm the exact saved entry with `query_audit_log` using the same organization and brand plus `tool_name: "manual_journal"` and `operation_id`. That read returns the immutable `input_json` and server timestamp. A correction is another entry linked through `correction_of`; do not edit the earlier row.

Keep entries concise. Do not include tokens, secrets, full email bodies, or unnecessary personal data in `notes` or metadata. Use short receipt and approval identifiers without URL query strings or fragments. The journal accepts only its named metadata fields. Use `create_next_action` for an actionable task and `list_next_actions` to follow its status; a journal `next_step` describes context but does not create a task.

`get_activity_timeline` shows candidate-linked journal and external records in the recruiter Activity tab. The existing Settings → Operations screen shows the organization and brand timeline, including entries without a candidate link. Its stable `before_ts`, `before_id`, and `before_source` cursor retrieves older pages. The candidate tab keeps the existing application notes, research activity, and audit sections. Neither view backfills past events or claims that every app or MCP operation was recorded.
